# Decisions

The settled decisions that shape Verichron Epoch, grouped by topic, each with
why it was made and where it was decided. Rules (`R<n>`) are in
[rules.md](rules.md); this page records the choices made within them.

**Keep it current:** a pull request that settles a decision adds its row here.
The page is append-only: a changed or reversed decision is recorded as a new row
that names the row it supersedes, and earlier rows are kept verbatim. Some older
rows carry inline change notes, added before this rule (2026-10-17); they are
kept as written.

## Product and builds

Until then the app and the report say indicator checks were not run | The user's decision (2026-10-12). Indicators are public STIX2 data and don't need mvt; matching on stored facts lets an earlier case be re-checked against a newer set without decrypting again | EPOCH-489 |
| The app owns one pinned, hash-verified core toolchain (mvt-ios, sqlite3, iLEAPP, the iPhone import tools and PostgreSQL 16) instead of examiner-installed tools. *Changed 2026-10-12: Ollama and the model moved from this toolchain to the separate AI module (row below)* *Changed 2026-10-13 (EPOCH-489): the backup decrypt's own environment replaces mvt-ios.* | Reproducibility is the product | EPOCH-439, 471 |

"mvt-runner" named one tool and a mechanism. ## Evidence identity

| Decision | Why | Where |
|---|---|---|
| `content_root` has exactly one definition and isn't user-selectable. A Merkle root may later be added as an extra sidecar field | It is the identity; two definitions would split one backup in two | EPOCH-401 |
| Evidence files live in `evidence/<label>/` under fixed names, with paths built only by `deriveEvidencePath()` | Appending a 64-hex root to a long label can exceed filename limits | EPOCH-401 |
| Manifests are content-addressed and never overwritten; the sidecar is replaced atomically, after its manifest exists | A crash must never leave a sidecar naming a missing manifest | EPOCH-401 |
| Devices are keyed by HMAC-SHA256(UDID, per-install secret); the raw UDID is never stored. The secret is a 0600 file outside the database, and a readable-by-others secret is refused | The same phone matches across backups without its UDID leaking; database access alone can't recover UDIDs | EPOCH-402, 404 |
| The UDID comes only from `Unique Identifier` / `Target Identifier`; `GUID` is refused | `GUID` is an iTunes backup ID, not the UDID | EPOCH-404 |

## Derivatives and provenance

| Decision | Why | Where |
|---|---|---|
| A derivative's identity is (evidence, kind, parent, provenance); its path is only a last-known location *Changed 2026-10-13 (EPOCH-489): there is no IOC-set derivative any more.* *Amended 2026-10-14 (EPOCH-517): the provenance key counts a preserved original as the database it came from, not its timestamped name, so a repeated decrypt with the same repair outcome is the same derivative; a repeated pass refreshes the row's params to the originals that exist now. On the reference backup, a forced decrypt with the identical outcome had become a second decrypt and a second iLEAPP output, and the report called all 46,434 facts "from an earlier pass".* | A moved workspace resumes; a new tool version, repair outcome or IOC set never overwrites old provenance | EPOCH-404, 406 |
| Completion markers record the evidence they were made from and their provenance. The processor withdraws a marker before redoing work, and registration refuses any mismatch | A changed backup must never have its old decrypt filed under the new evidence | EPOCH-404 |
| The processor owns mvt's data and config folders, refuses `MVT_STIX2`, and checks each run against a private, hashed copy of the IOCs *Changed 2026-10-13 (EPOCH-489): mvt-ios is removed; see the rows below.* | The recorded IOC set must be exactly the one used | EPOCH-406 |
| iLEAPP's output becomes its own derivative (parent: the decrypt), in `<workspace>/ileapp/<label>/` | Its files are iLEAPP's output, not the decrypt's (R7); a shared directory mixed backups together | EPOCH-416 |
| The processor runs iLEAPP, as its third derivative after decrypt and check-backup, and marks the output complete with `.ileapp_ok`; the iLEAPP bridge only ingests the registered output. iLEAPP's provenance is its submodule commit, and a checkout with local changes is refused. The submodule lives at `tools/ileapp/iLEAPP`, beside its environment *Changed 2026-10-13 (EPOCH-489): it is now the second derivative; check-backup is removed.* | One component makes derivatives and the stages only read them, so iLEAPP output gets the same markers, reuse rules and registration as mvt's. iLEAPP's self-reported version (2026.3.0) does not match its release tag (v2026.3.1), so only the commit identifies the code that ran | EPOCH-416 |
| Each stage declares the derivative it reads (`reads` in `stage.json`: `decrypted`, `mvt_results` or `ileapp_output`), and the orchestrator passes that derivative's id and directory (`--derivative-id`, `--derivative-path`). `requiresResultsPath` is removed *Changed 2026-10-13 (EPOCH-489): `mvt_results` is removed; stages read `decrypted` or `ileapp_output`.* | A stage reads exactly the derivative its facts are filed under, from a path it is given rather than one it infers (R7, R18) | EPOCH-416 |
| A decrypt fails when mvt-ios reports any file it couldn't decrypt, and names them; no marker is written. Every mvt call runs with a wide `COLUMNS`, so each log message stays on one line *Changed 2026-10-13 (EPOCH-489): the same rule holds for the new decrypt, which fails unless every listed file is written.* | mvt skips such a file and still exits 0, so its exit code alone would vouch for an incomplete decrypt. In a pipe, rich wraps its log at 80 columns and splits each message | EPOCH-486 |
| iLEAPP has a limit per module, not per run: each module, and the setup and report around them, may run 60 minutes (`--ileapp-module-timeout`). Each module's timing is written to `logs/<backup>.ileapp-modules.json`, and a stopped run names the module and the modules that didn't run | A whole-run limit (30 minutes before) stops a slow but healthy run on a large backup; a per-module limit only stops a stuck module, as Autopsy limits each ingest module rather than the whole job | EPOCH-487 |
| Backups are decrypted with `iphone_backup_decrypt` 0.10.0 (MIT), pinned exactly in its own environment (`tools/decrypt`), into the same iTunes layout (`Manifest.db`, `XX/<fileID>`, the root plists) that iLEAPP reads with `-t itunes`. The password arrives only in `BACKUP_PASSWORD`; a wrong one has its own exit code (3). The decrypt fails unless every file with `flags=1` in `Manifest.db` was written, and writes only into an empty folder. It runs in its own tracked process group and is stopped when it writes nothing for 30 minutes (`--decrypt-stall-timeout`); a long decrypt that keeps writing is never stopped, as with iLEAPP's per-module limit. Root plists that are links or not regular files are refused before anything is written. Its two uses of the library's internals (the unlocked keybag, the chunked file decrypt) are why the pin is exact | Chosen by test on the real 77 GB backup over `idevicebackup2 unback`: complete (11,223 of 11,223 files), the original unchanged, iLEAPP reads it to the end. `unback` needs the phone connected, writes inside the backup folder, has an open bug that stops it part way (libimobiledevice #1147), and writes device paths that lose each file's link to its manifest entry | EPOCH-489 |
| Before decrypting, Prepare Evidence checks workspace free space with `statfs`. The estimate is one backup-sized decrypted tree plus an iLEAPP margin scaled from the reference run's 71 GB output for 77,217,764,077 backup bytes. An `ENOSPC` fails the step and leaves its completion marker unwritten | The reference run's decrypted tree was about the backup's size and iLEAPP output added a further 71 GB; detecting a shortfall before a long decrypt avoids late failure, and a partial derivative must never be marked complete | EPOCH-496 |
| iLEAPP never runs `unifiedlog_iterator`: the processor sets `ILEAPP_UNIFIEDLOG_ITERATOR` to a value that is not an executable file, so iLEAPP's `logarchive` module logs that and carries on without it | The user's decision (2026-10-12) to avoid it. iLEAPP reads that variable before any other location, so nothing on the machine can be picked up instead | EPOCH-489 |
| The device's crash logs are a derivative of their own (`crash_reports`), read by the crash stage; the stage never searches a backup for them. They will be copied from the device at pull time with `idevicecrashreport -k` (EPOCH-514), and read from full-filesystem extractions (EPOCH-515). Until then the stage is recorded as skipped, with the reason, and the report lists it under Not Examined *Amended 2026-10-14 (EPOCH-514): the pull copies them after a completed backup into `<UDID>.crash-reports/` beside it, recorded in `<UDID>.crash-reports.json` once finished; the processor copies them into `crash_reports/<label>/` and verifies the copy's content root; registration files them under the backup's evidence with no parent. A failed copy is recorded in the pull record and doesn't fail the completed backup. idevicecrashreport is run only by `crashReports.ts`, always with `-k`, and a `Move:` line fails the copy.* *Amended 2026-10-15 (EPOCH-519, the project owner): the device must stay unlocked until the copy ends, since a locked device refuses it. A failed copy can be made again, first on the pull's result while the device is connected, or later; only from the device the backup came from, never over an existing copy, recorded as its own pull-record line, and with the report stating how long after the backup it was made, because the device's reports change during the day.* | On the real reference backup, `Manifest.db` listed no file under `DiagnosticReports` or `CrashReporter`, and the stage succeeded with nothing, which read as "no crashes" when it meant "never looked". `idevicecrashreport` moves reports off the device unless `-k` is given, and the device is evidence | EPOCH-447 (the project owner, 2026-10-14) |
| A crash report's time is its metadata line's `timestamp`, for every report; a JSON body's own `captureTime` or `date` is kept in `fields.body_time`, and `fields.time_source` names the source. A report whose body isn't JSON (text, further JSON lines, or bytes that aren't UTF-8) is ingested from its metadata line, with the body kept exactly | One standard: all 230 reports from the reference device have the metadata timestamp, only 15 have a body time, and in those 15 the two agree to within a second. Neither is known to be more trustworthy; both are written by the device into the same file. Failing the 18 reports without a JSON body would have failed the stage on every run | EPOCH-447 (the project owner, 2026-10-14) |
| The report is written to `<workspace>/reports/<label>/investigation_report.md`; the orchestrator passes every stage `--report-path`, and the app finds the report from the run's decrypt (`getRunReportLocation`). The report has a "Not Examined" section naming indicator checks and AI-assisted analysis | The report used to live in mvt's results folder, which no longer exists. Saying what wasn't examined keeps an absent check from reading as a clean device (R21) | EPOCH-489 |
| A tool that runs in its own Python environment (the decrypt, iLEAPP) records that environment in its identity: `tool.environment`, the sha256 of the Python version and every installed distribution with its version, as the tool's own interpreter lists them. iLEAPP output made by the same commit in a different environment is made again, as a new derivative; a finished decrypt is kept when only its tool changed, as before | Changing iLEAPP's environment (pi-heif in place of pillow-heif) changes what it produces without changing its commit, so the commit alone would record new output as made by the same tool and leave old output in place. The digest is read from what is installed, not from a lockfile, so it describes what actually ran | Project owner, 2026-10-17; EPOCH-439 |

## Runs and completeness

| Decision | Why | Where |
|---|---|---|
| `workspace.json` is the source of every workspace-owned path. The processor publishes it atomically under the workspace lock; workspace-owned paths are relative to its root, while the original external source path remains provenance. The orchestrator and app resolve paths only through this manifest and refuse missing or invalid manifests; stages still receive explicit paths | Directory conventions had been independently reconstructed by the processor, orchestrator and app, so renaming one output could misregister evidence or send a stage to the wrong files (R18) | EPOCH-427 |
| *Amended 2026-10-17 (VER-120):* The `runs/<label>/<run_id>.json` location in EPOCH-409 and the app's `decrypted/<label>` path handoff in EPOCH-530 are superseded. Consumers resolve each run-summary and decrypt path from the selected backup's `workspace.json` entry. The earlier entries remain as historical rationale, not current path contracts | Fixed directory names must not remain a competing source of path truth after adopting the workspace manifest | VER-120 |
| A stage's order has one owner, its `stage.json`: the orchestrator records it on each stage row (`pipeline_stage_status.stage_order`, migration 0014), disabled stages included, and readers order a run's stages by it in SQL. The reader's hard-coded `CANONICAL_STAGE_ORDER` is gone | It had drifted from the real stages (only `crash` matched), so the app showed stages in arbitrary order (R2). Rows from before 0014 have no order and aren't backfilled: the migration refuses a database with runs (the owner's decision, 2026-10-15) | EPOCH-414 |
| Discovery validates each `stage.json` against `stage-manifest.schema.json` itself (ajv 8, MIT), replacing a hand-written copy of it. A manifest that doesn't match refuses the whole run, naming the file and each failing field, including a misspelled one (the schema sets `additionalProperties: false`) | A second definition had to be kept in step by hand for every new field. A stage silently left out of a forensic run is worse than a run that won't start | EPOCH-444 |
| The orchestrator reports to its caller in typed events: one stdout line each, `@@verichron ` plus JSON, defined by one zod contract and validated before writing and on reading ([architecture](architecture.md#orchestrator-events)). A stage's stdout is relayed line by line, and a stage line that starts with the prefix is tagged with the stage's name. The app takes the running stage and the runs a call created only from events, not from log text; an invalid event line is kept as text and changes nothing. IDs are checked as PostgreSQL stores them (`z.guid()`) | The app couldn't learn which runs a process created, which EPOCH-435's close-out by run ID needs, and it took the running stage from a free-text log line. The orchestrator relayed each stage's stdout byte for byte, so with a prefix alone a stage, or a value it echoed from the evidence, could have forged an event. A separate file descriptor would have been stronger, but the app runs the orchestrator through `pnpm`, and a child started with `pnpm exec` gets no file descriptor beyond the standard three (checked 2026-10-17: writing to fd 3 fails with `EINVAL`) | EPOCH-443 |
| Supersedes the row above in part: with `--output events`, how the app runs it, the orchestrator writes only events, and relays each stage's stdout and stderr as `stage:output` events, the line a field inside the event, instead of tagging a prefixed line with the stage's name. With `--output text`, the command line's default, it writes the same events as human lines. A failed stage's `stage:finished` gives its reason, the last line it wrote to stderr or its stop reason. The app also refuses an event that program does not emit | The task log needs every line typed and levelled, and a stage's stderr, kept until now only in `error_message`, is what explains a failure (EPOCH-569). With the line inside an event, no prefix check is needed for a stage to be unable to forge one | EPOCH-570, EPOCH-445; [event-log.md](event-log.md) |
| The task log has two views, Summary (the default) and Full log. A stage reports what it did with `stage_report.report()`, read by the orchestrator as `stage:log`; its raw output stays `debug`. A stage's notes have a kind: information, for review or warning. A note for review is something in the evidence worth an examiner's look (an impossible or future time, a value stored encoded or corrected for a tool defect, an indicator match), shown as "For review" and never as a warning or a lead. Only notes for review and warnings are stored as a succeeded stage's warnings | In the first real Analyze log every useful line was a stage's raw output, so all of it read DEBUG and a summary had nothing to show. Every note was stored as a warning, so the indicator stage read "with warnings" on every clean check. "Warning" overstates a note for review, and "lead" is the AI module's word | Project owner, 2026-10-18; EPOCH-570; [event-log.md](event-log.md) |
| Completeness is one database view, `run_completeness`; `skipped` never makes a run incomplete. No component re-derives it | R23 | EPOCH-404 |
| Every rerun creates a new run; finished runs are never reopened | Runs stay append-only | EPOCH-408 |
| Each run exports its own summary from the database to `runs/<label>/<run_id>.json`; one orchestrator call's result goes to a file its caller names (`--summary-path`), never a shared workspace file | A single workspace-root `analysis-summary.json` was overwritten by every call, so a rerun of one backup erased the others' results. Merging into one file was rejected: it needs locking and adds the second writer R23 rules out | EPOCH-409 |
| Resume skips evidence only if a complete run ran every stage enabled now, at the parser version declared now, against the derivative it would read now *Amended 2026-10-14 (EPOCH-447): a stage skipped because the evidence lacks a derivative only some acquisitions produce (crash logs never acquired) counts while that is still so, matched by its recorded reason; a disabled stage's skip never counts.* | A version bump, newly enabled stage or new results set must not be skipped as done | EPOCH-404, 406 |
| A run with no registered evidence is reported as "not registered, not read", never as "nothing found" | Not reading is not finding nothing | EPOCH-403 |
| *Settled 2026-10-17:* a run records its orchestrator's `host` and `pid` and, once ended, `ended_reason` and `ended_detail` (migration 0017, which refuses a database with runs). The orchestrator closes its own failure as `crashed`. The app closes a call's runs by ID from `run:created` (EPOCH-443), as `cancelled`, `timeout` or `crashed`, and sweeps open runs on this host whose process is gone as `abandoned`, at start and before reporting a workspace's status, which finds the workspace's evidence by its sidecars' content roots. A stage left `pending` or `running` on an ended run shows "stopped", and Forensic Records says when a fact-writing stage's latest attempt was interrupted (`interrupted_stages`, EPOCH-561). The wording was approved by the owner | The stage rows had been rewritten to `failed` in four places, and runs were found by path. Process liveness on this host is what can be checked: a reused pid can only leave a dead run open longer, never close a live one. A stage that was interrupted recorded none of its failed items, so an empty still-failing list could read as "nothing missing" | EPOCH-435, EPOCH-561 |
| Abandoned runs are closed by run id and process liveness, recording why they ended, never by rewriting stage rows or matching paths | History stays truthful, and one process can't touch another's runs | EPOCH-435 |
| No stage is disabled to make a build look stable without explicit discussion | Hiding a broken stage over-claims what the build does | Team decision, 2026-10-08 |
| Analyze refuses a database with pending migrations (no `schema_migrations` ledger, or a migration file it doesn't list) before registering anything, and names them; it never applies migrations itself | A database behind the code failed deep inside registration with a constraint error, after a long successful prepare. Who applies migrations automatically is the Lab build's decision (EPOCH-475, 477) | EPOCH-498 |

## Facts and ingest

| Decision | Why | Where |
|---|---|---|
| There is one fact writer, `db_writer.py`. `etl-db-writer` is Python-only (writer, `migrate.py`, migrations) | R2; nothing used the TypeScript writer, and keeping two in step was recurring cost | EPOCH-452 |
| `parserVersion` is an incrementing integer declared in each `stage.json` and passed by the orchestrator | One owner of unit identity (R2, R16); text versions sort wrongly | EPOCH-402, 404 |
| Read selection rules live in database views (`current_forensic_records`, `forensic_records_history`) | The report and app must agree (R27); an unfinished re-parse must never hide finished facts | EPOCH-403 |
| A reader may count what a run produced by matching the run against a fact unit's `produced_by_runs` label (a stage card's "N records from M units"). Facts are still shown per evidence; any other route from a run to facts (a `run_id` filter, a join through `pipeline_runs`) fails the R7 guard in `scripts/test_evidence_reads.py` | R7 labels facts with the runs that produced them; reading that label is audit, not attaching facts to a run. The guard had been stricter than the rule | EPOCH-501 |
| Completed ingest rows are immutable, so per-run attribution lives in the append-only `ingest_run_links` table rather than on `ingested_files`; this supersedes EPOCH-501's `produced_by_runs` storage choice while retaining its R7 policy. The `purge_evidence(evidence_id, reason)` function is the only route to delete completed facts and ledger rows, and records the database actor and reason in immutable custody events | R9 requires database-level immutability while R7 still requires run attribution; an immutable relation preserves both without mutating completed ledger rows | VER-105 |
| An iLEAPP plugin that errored is recorded with the output it belongs to (the `.ileapp_ok` marker's `modules`, stored as the derivative's provenance) and stated in the report's "Not Examined", with the artifact, file count and iLEAPP's error. It doesn't fail the stage. An output without a readable module list gets no marker | iLEAPP exits 0 when a plugin errors, so the failure was invisible: on the 77 GB reference backup, `ZaloChats` errored (`IndexError` at line 159) and nothing said so. The error is inside iLEAPP and the same on every run, so failing the stage would keep every run Incomplete with no retry that could help | EPOCH-457 |

## Crash-log retry

| Decision | Why | Where |
|---|---|---|
| A finished existing backup can offer a crash-log retry outside the pull result only when the exact originating device is connected and neither crash-log destination exists. The user is told to unlock and keep the device connected before confirming the copy; after success, they prepare the backup again to include the new acquisition. The renderer receives only a process-local opaque device reference and display name, never the device ID from this retry lookup | The pull may have finished without crash logs, and the device's reports can change later. Eligibility is checked against the finished backup, its recorded device identity and both canonical copy paths; the main process resolves the opaque reference, and the copy operation rechecks the device and destination before writing | EPOCH-520 (VER-202) |
