# Decisions

The settled decisions that shape Verichron Epoch, grouped by topic, each with
why it was made and where it was decided. Rules (`R<n>`) are in
[rules.md](rules.md); this page records the choices made within them.

**Keep it current:** a pull request that settles a decision adds or edits its row
here. A reversed decision is edited in place, with the reversal noted; it is
never silently deleted.

## Product and builds

| Decision | Why | Where |
|---|---|---|
| The first release is a **Lab build**: air-gapped, built separately, with networking blocked and no setting to re-enable it. A Personal build comes later from the same core | Do the hardest work first so integrity is built in; a flag on one binary is weaker evidence for an auditor | EPOCH-438 |
| In Lab, IOC sets and tools are imported from media, hashed and recorded. Nothing is downloaded, and mvt's update checks are off *Changed 2026-10-13 (EPOCH-489): mvt is removed; indicator sets come in as signed bundles (EPOCH-492).* | Air gap and chain of custody | EPOCH-438, 439 |
| The project moves off mvt-ios completely: it no longer decrypts backups, checks indicators or feeds the AI stage. Indicator checks return as the project's own matching on its extracted facts, against versioned, hashed indicator sets (EPOCH-490 to 493). Until then the app and the report say indicator checks were not run | The user's decision (2026-10-12). Indicators are public STIX2 data and don't need mvt; matching on stored facts lets an earlier case be re-checked against a newer set without decrypting again | EPOCH-489 |
| The app owns one pinned, hash-verified core toolchain (mvt-ios, sqlite3, iLEAPP, the iPhone import tools and PostgreSQL 16) instead of examiner-installed tools. *Changed 2026-10-12: Ollama and the model moved from this toolchain to the separate AI module (row below)* *Changed 2026-10-13 (EPOCH-489): the backup decrypt's own environment replaces mvt-ios.* | Reproducibility is the product | EPOCH-439, 471 |
| No custom-tuned model until a labelled evaluation set shows what a tune would fix | A tune must be justified and defensible | EPOCH-441 |
| Lab requirements (network enforcement, signing, audit artifacts) come from practicing examiners, not from us alone | Only they and their auditors can answer them | EPOCH-440 |
| The two builds are named **Lab Edition** and **Personal Edition**. "Personal" was chosen over "Home" | "Personal" states whose device and data the edition is for; "Home" describes a place and implies examining other household members' devices | Linear projects "Verichron Epoch: Lab Edition 1.0" and "Personal Edition 1.0" |
| The Personal Edition empowers its user: it keeps the core's full capability, and adds restrictions only where the law requires them | The product serves the person examining their own device; it does not assume a paternal role | Personal Edition 1.0 |
| The workflow vocabulary is **acquire → process → extract (ETL) → analyze → report**. The component that verifies evidence and produces derivatives is the **processor** (formerly mvt-runner); the orchestrator coordinates extract, analyze and report | One accurate name per step, in the terms examiners use. "mvt-runner" named one tool and a mechanism. "Transformer" was rejected: in forensics it implies altering evidence, in ETL terms the extractors already transform, and it is a homonym of the model architecture | EPOCH-462 |
| The AI module (the inference runtime and a model pinned by digest) is a separate, optional bundle with its own signed manifest, naming the core versions it works with. Lab imports it from media. The alpha gates on the core only | The weights are large, and their licensing and hardware needs differ from the core's. The core must be verifiable and usable without it | EPOCH-471, 476 |
| The Lab alpha supports Debian 13 on amd64, built in a container pinned by digest so the build floor equals the support floor; arm64 comes later. AVX2 is required by the AI module only. macOS paths in the code are for development and are not a supported Lab platform | One glibc floor and reproducible builds. Requiring AVX2 for the core would exclude older lab machines for no gain | EPOCH-471, 478 |
| The Lab build ships as a tarball with one signed manifest covering every file, and runs without root; administrator rights are needed only for the udev rules and the usbmuxd service. It includes PostgreSQL 16, which the app manages and reaches over a unix socket only. Published hashes and an SBOM let the bundle be checked before it crosses the air gap | Least privilege, and an examiner can see what each admin step is for. No examiner-installed database and no TCP port | EPOCH-471, 477, 478 |
| In the Lab build, the iPhone import tools ship prebuilt in the bundle, verified by its manifest. The guided setup (downloads, apt or Homebrew, building from source) is for the Personal build and development only | Lab blocks the network and installs nothing it hasn't imported from media; the guided setup downloads | EPOCH-472 |
| Upgrades run in place: the new version applies the numbered migrations it carries, after a mandatory export of the database whose hash is recorded. Only derived tables may be rebuilt; the custody log (`evidence_events`) and the examiner's decisions on leads are never regenerated | Those records come from people and events, not from the backups, so rebuilding the database would destroy them | EPOCH-475 |
| The public roadmap is published from Linear capability issues labelled **Public**: only their title, lane and mapped status leave Linear, through a serverless webhook receiver with a nightly reconcile. The rules are in [roadmap.md](roadmap.md) | The Linear workspace is private; default-deny publishing keeps ticket content out of public places while the page stays current at this pace of work | EPOCH-471, 480, 481 |

## AI

| Decision | Why | Where |
|---|---|---|
| The LLM produces **leads, not evidence**. Its findings appear in their own "AI-assisted leads" section, each citing records with its model and prompt version, and the examiner confirms or dismisses each one (recorded append-only). Leads run in Lab too, when the AI module is installed (*changed 2026-10-12: the module became optional*) | AI's pattern-finding has a role, but must never alter evidence or replace the examiner's opinion | EPOCH-442 |
| An unreachable model fails the analysis stage; it never reports "no findings" | "Not analysed" must not read as "nothing suspicious" | EPOCH-450 |
| When the AI module isn't installed, the analysis stage is recorded as skipped with that reason, and the report says AI-assisted analysis was not run. An installed module that is unreachable still fails the stage | Leaving the module out is a deliberate configuration; an unreachable model is a fault. Both meet R21 because the report says which happened | EPOCH-474 |
| The AI stage (`apps/analysis`) is out of the pipeline, with no `stage.json`, until it reads the project's own facts; the report says AI-assisted analysis was not run | Its only input was mvt-ios's check-backup JSON, which EPOCH-489 removes. The user agreed to remove it for now (2026-10-13) rather than keep mvt for it or rebuild it ahead of EPOCH-442's design | EPOCH-489, 442 |

## Evidence identity

| Decision | Why | Where |
|---|---|---|
| `content_root` has exactly one definition and isn't user-selectable. A Merkle root may later be added as an extra sidecar field | It is the identity; two definitions would split one backup in two | EPOCH-401 |
| Evidence files live in `evidence/<label>/` under fixed names, with paths built only by `deriveEvidencePath()` | Appending a 64-hex root to a long label can exceed filename limits | EPOCH-401 |
| Manifests are content-addressed and never overwritten; the sidecar is replaced atomically, after its manifest exists | A crash must never leave a sidecar naming a missing manifest | EPOCH-401 |
| Devices are keyed by HMAC-SHA256(UDID, per-install secret); the raw UDID is never stored. The secret is a 0600 file outside the database, and a readable-by-others secret is refused | The same phone matches across backups without its UDID leaking; database access alone can't recover UDIDs | EPOCH-402, 404 |
| The UDID comes only from `Unique Identifier` / `Target Identifier`; `GUID` is refused | `GUID` is an iTunes backup ID, not the UDID | EPOCH-404 |

## Derivatives and provenance

| Decision | Why | Where |
|---|---|---|
| A derivative's identity is (evidence, kind, parent, provenance); its path is only a last-known location *Changed 2026-10-13 (EPOCH-489): there is no IOC-set derivative any more.* | A moved workspace resumes; a new tool version, repair outcome or IOC set never overwrites old provenance | EPOCH-404, 406 |
| Completion markers record the evidence they were made from and their provenance. The processor withdraws a marker before redoing work, and registration refuses any mismatch | A changed backup must never have its old decrypt filed under the new evidence | EPOCH-404 |
| The processor owns mvt's data and config folders, refuses `MVT_STIX2`, and checks each run against a private, hashed copy of the IOCs *Changed 2026-10-13 (EPOCH-489): mvt-ios is removed; see the rows below.* | The recorded IOC set must be exactly the one used | EPOCH-406 |
| iLEAPP's output becomes its own derivative (parent: the decrypt), in `<workspace>/ileapp/<label>/` | Its files are iLEAPP's output, not the decrypt's (R7); a shared directory mixed backups together | EPOCH-416 |
| The processor runs iLEAPP, as its third derivative after decrypt and check-backup, and marks the output complete with `.ileapp_ok`; the iLEAPP bridge only ingests the registered output. iLEAPP's provenance is its submodule commit, and a checkout with local changes is refused. The submodule lives at `tools/ileapp/iLEAPP`, beside its environment *Changed 2026-10-13 (EPOCH-489): it is now the second derivative; check-backup is removed.* | One component makes derivatives and the stages only read them, so iLEAPP output gets the same markers, reuse rules and registration as mvt's. iLEAPP's self-reported version (2026.3.0) does not match its release tag (v2026.3.1), so only the commit identifies the code that ran | EPOCH-416 |
| Each stage declares the derivative it reads (`reads` in `stage.json`: `decrypted`, `mvt_results` or `ileapp_output`), and the orchestrator passes that derivative's id and directory (`--derivative-id`, `--derivative-path`). `requiresResultsPath` is removed *Changed 2026-10-13 (EPOCH-489): `mvt_results` is removed; stages read `decrypted` or `ileapp_output`.* | A stage reads exactly the derivative its facts are filed under, from a path it is given rather than one it infers (R7, R18) | EPOCH-416 |
| A decrypt fails when mvt-ios reports any file it couldn't decrypt, and names them; no marker is written. Every mvt call runs with a wide `COLUMNS`, so each log message stays on one line *Changed 2026-10-13 (EPOCH-489): the same rule holds for the new decrypt, which fails unless every listed file is written.* | mvt skips such a file and still exits 0, so its exit code alone would vouch for an incomplete decrypt. In a pipe, rich wraps its log at 80 columns and splits each message | EPOCH-486 |
| iLEAPP has a limit per module, not per run: each module, and the setup and report around them, may run 60 minutes (`--ileapp-module-timeout`). Each module's timing is written to `logs/<backup>.ileapp-modules.json`, and a stopped run names the module and the modules that didn't run | A whole-run limit (30 minutes before) stops a slow but healthy run on a large backup; a per-module limit only stops a stuck module, as Autopsy limits each ingest module rather than the whole job | EPOCH-487 |
| Backups are decrypted with `iphone_backup_decrypt` 0.10.0 (MIT), pinned exactly in its own environment (`tools/decrypt`), into the same iTunes layout (`Manifest.db`, `XX/<fileID>`, the root plists) that iLEAPP reads with `-t itunes`. The password arrives only in `BACKUP_PASSWORD`; a wrong one has its own exit code (3). The decrypt fails unless every file with `flags=1` in `Manifest.db` was written, and writes only into an empty folder. It runs in its own tracked process group and is stopped when it writes nothing for 30 minutes (`--decrypt-stall-timeout`); a long decrypt that keeps writing is never stopped, as with iLEAPP's per-module limit. Root plists that are links or not regular files are refused before anything is written. Its two uses of the library's internals (the unlocked keybag, the chunked file decrypt) are why the pin is exact | Chosen by test on the real 77 GB backup over `idevicebackup2 unback`: complete (11,223 of 11,223 files), the original unchanged, iLEAPP reads it to the end. `unback` needs the phone connected, writes inside the backup folder, has an open bug that stops it part way (libimobiledevice #1147), and writes device paths that lose each file's link to its manifest entry | EPOCH-489 |
| iLEAPP never runs `unifiedlog_iterator`: the processor sets `ILEAPP_UNIFIEDLOG_ITERATOR` to a value that is not an executable file, so iLEAPP's `logarchive` module logs that and carries on without it | The user's decision (2026-10-12) to avoid it. iLEAPP reads that variable before any other location, so nothing on the machine can be picked up instead | EPOCH-489 |
| The report is written to `<workspace>/reports/<label>/investigation_report.md`; the orchestrator passes every stage `--report-path`, and the app finds the report from the run's decrypt (`getRunReportLocation`). The report has a "Not Examined" section naming indicator checks and AI-assisted analysis | The report used to live in mvt's results folder, which no longer exists. Saying what wasn't examined keeps an absent check from reading as a clean device (R21) | EPOCH-489 |

## Runs and completeness

| Decision | Why | Where |
|---|---|---|
| Completeness is one database view, `run_completeness`; `skipped` never makes a run incomplete. No component re-derives it | R23 | EPOCH-404 |
| Every rerun creates a new run; finished runs are never reopened | Runs stay append-only | EPOCH-408 |
| Each run exports its own summary from the database to `runs/<label>/<run_id>.json`; one orchestrator call's result goes to a file its caller names (`--summary-path`), never a shared workspace file | A single workspace-root `analysis-summary.json` was overwritten by every call, so a rerun of one backup erased the others' results. Merging into one file was rejected: it needs locking and adds the second writer R23 rules out | EPOCH-409 |
| Resume skips evidence only if a complete run ran every stage enabled now, at the parser version declared now, against the derivative it would read now | A version bump, newly enabled stage or new results set must not be skipped as done | EPOCH-404, 406 |
| A run with no registered evidence is reported as "not registered, not read", never as "nothing found" | Not reading is not finding nothing | EPOCH-403 |
| Abandoned runs are closed by run id and process liveness, recording why they ended, never by rewriting stage rows or matching paths | History stays truthful, and one process can't touch another's runs | EPOCH-435 |
| No stage is disabled to make a build look stable without explicit discussion | Hiding a broken stage over-claims what the build does | Team decision, 2026-10-08 |
| Analyze refuses a database with pending migrations (no `schema_migrations` ledger, or a migration file it doesn't list) before registering anything, and names them; it never applies migrations itself | A database behind the code failed deep inside registration with a constraint error, after a long successful prepare. Who applies migrations automatically is the Lab build's decision (EPOCH-475, 477) | EPOCH-498 |

## Facts and ingest

| Decision | Why | Where |
|---|---|---|
| There is one fact writer, `db_writer.py`. `etl-db-writer` is Python-only (writer, `migrate.py`, migrations) | R2; nothing used the TypeScript writer, and keeping two in step was recurring cost | EPOCH-452 |
| `parserVersion` is an incrementing integer declared in each `stage.json` and passed by the orchestrator | One owner of unit identity (R2, R16); text versions sort wrongly | EPOCH-402, 404 |
| Read selection rules live in database views (`current_forensic_records`, `forensic_records_history`) | The report and app must agree (R27); an unfinished re-parse must never hide finished facts | EPOCH-403 |
| A reader may count what a run produced by matching the run against a fact unit's `produced_by_runs` label (a stage card's "N records from M units"). Facts are still shown per evidence; any other route from a run to facts (a `run_id` filter, a join through `pipeline_runs`) fails the R7 guard in `scripts/test_evidence_reads.py` | R7 labels facts with the runs that produced them; reading that label is audit, not attaching facts to a run. The guard had been stricter than the rule | EPOCH-501 |
| Row failures are strict: any failed row rolls back its whole file, which stays retryable. No tolerant mode | Committing the rows that survived marked the file complete, so failed rows were never retried | EPOCH-417 |
| *Settled 2026-10-14:* an iLEAPP artifact with no rows is filed as a completed unit with `record_count = 0` (reversing EPOCH-461's "files nothing"). iLEAPP records keep identity fields (`process_name`, `bundle_id` and the rest) null; they are never filled from columns whose headers look like them | Examined and empty is a finding the evidence should show, and later runs skip it instead of re-reading it. Choosing a column by its header's spelling is the guessing EPOCH-461 removed; the values stay under their original headers | EPOCH-417 |
| Retry is per file, through a rerun. Failed files are persisted so they can be shown, but there's no per-record retry | A failed file leaves no ledger row, so a rerun retries exactly what failed | EPOCH-432 |
| `ETLRunResult.ok(n)` counts records written by this run; an already-ingested file is `ok(0)` plus a note | Summaries were wrong on resumed runs | EPOCH-421 |
| A stage that succeeds keeps its stderr as `warnings`; `error_message` is for failures only, and warnings never change run state | Coverage gaps were being discarded on success | EPOCH-420 |

## Time and extraction

| Decision | Why | Where |
|---|---|---|
| The iLEAPP bridge reads results only from `_lava_artifacts.db`, guided by its manifest `_lava_data.lava`: one ingest unit per artifact table, original column headers, and `event_time` from the artifact's declared `datetime` column. Exports, the HTML report and iLEAPP's input copies (`data/`, `media/`) are never read | `_lava_artifacts.db` is iLEAPP's complete, typed output; its plugins already convert each source's time format to UTC, so guessing again could only add errors | EPOCH-461 |
| *Settled 2026-10-08 (EPOCH-461):* an artifact table's unit identity is a sha256 over everything its records carry: the artifact's name, module, category and source path, its columns and headers in order, its declared types in declared order, and its rows (`file_path` `_lava_artifacts.db#<table>`), with no ledger schema change. `event_time` is the first declared `datetime` column, and every one is kept in `fields`. A declared time that isn't numeric Unix seconds gives `event_time = null`, keeps the raw value, and is counted in the stage's notes | A content hash identifies the artifact as precisely as a file hash identifies a file, so an unchanged table from a re-run of iLEAPP is a dedup hit. iLEAPP plugins list the primary time first. A value iLEAPP couldn't convert is reported, never guessed (R11), and one bad row doesn't block its artifact | EPOCH-461 |
| Numeric timestamps need a declared epoch, or must fall between 2007-06-29 and now + 1 day; otherwise null. An unparseable time column gives null, never another column's value. *Amended 2026-10-08:* for iLEAPP this no longer applies, because its plugins declare time columns (EPOCH-461); whether the window remains as a reported check on iLEAPP's values is decided there | A plausible but wrong date is worse than none | EPOCH-419, 461 |
| mvt's indicator types are kept verbatim as explicit fields, not mapped to our own enum *Changed 2026-10-13 (EPOCH-489): mvt's matches are removed; indicator types are designed afresh in EPOCH-490 and 491.* | An enum with an "unknown" fallback loses information | EPOCH-446 |
| The report states which fact types it doesn't show, with counts | "Not shown" must not read as "not found" | EPOCH-448 |
| The report's Run Completeness table leaves out the report's own stage, and says instead which run generated the report and when | The report is written while its own stage is still running, so that row always read "running" in a finished document (the user chose this over labelling the row "this report") | EPOCH-499 |
| The report summarizes iLEAPP output per artifact (counts and time range) and doesn't list rows | Output can reach 100k+ rows; rows belong in the app | EPOCH-434 |

## Configuration, secrets and tooling

| Decision | Why | Where |
|---|---|---|
| The database URL comes only from `DATABASE_URL` or `DB_*`; there is no URL flag and no hard-coded credential | A URL flag puts the password on the command line (R30) | EPOCH-423, 424 |
| Contract parity across TS, Python and JSON schemas is validated sync (`sync_contracts.py --check` and tests), not code generation | Already enforced in CI, with tests for each mirror | EPOCH-451 |
| No class hierarchies for stages, extractors or devices; plain functions plus `stage.json` | Every audit that proposed one found the need already met more simply | Audits, 2026-10-08 |
| The unused Qdrant service is removed | Unused network services are attack surface | EPOCH-438 |
| Tool versions are pinned exactly, each in the one file its tool enforces: Node, pnpm and uv in `mise.toml` (pnpm's exact version in `packageManager`), Python in `.python-version` | Setup must give the same result on every machine and in CI; a minimum version (`>=`) let machines drift | EPOCH-458 |
| **Python 3.14**, always a uv-managed CPython; system interpreters are never used | Current release, supported to 2030, and the version iLEAPP builds with; 3.12 is security-only, ends in 2028 and forces an unmaintained numpy | EPOCH-458 |
| **Node 24 LTS** and **Electron 44**, pinned to the latest patch; Node moves only together with Electron | Electron 44 bundles Node 24, so tooling and app runtime match; Electron patches carry Chromium security fixes | EPOCH-458 |
| mvt and iLEAPP each run from their own pinned uv environment (`tools/mvt`, `tools/ileapp`), not from the workspace venv *Changed 2026-10-13 (EPOCH-489): `tools/decrypt` replaces `tools/mvt`.* | Their exact dependency pins conflict (`packaging` 26.x against 24.1); sharing one venv had silently held mvt at an outdated release | EPOCH-458 |
| Setup checks every prerequisite before installing and installs only from lockfiles; Dependabot proposes dependency updates | Failures name the missing prerequisite instead of surfacing deep inside an install; exact pins stay current only if updates are proposed | EPOCH-458 |
| iPhone import tools (Linux, macOS): the app shows every requirement with its status, installs missing system packages through the OS's administrator prompt (pkexec; Homebrew on macOS needs none), and builds libplist 2.8.0, libimobiledevice-glue 1.3.3, libusbmuxd 2.1.1, libtatsu 1.0.5 and libimobiledevice 1.4.0 from release tarballs pinned by SHA-256 into its own tools folder. A manifest written after `idevicebackup2` is verified marks them installed | The tool acquires evidence, so every machine must build the same verified code and record it. Release tarballs need no autotools. Users see what's needed and what they have before anything runs. Windows keeps its WSL path for now. *Changed 2026-10-12: the Lab build ships these tools prebuilt instead (EPOCH-472)* | EPOCH-465 |
| iPhone pulls stay encrypted-only. When the device's encrypted backups are off, the app asks before turning them on, runs `idevicebackup2 encryption on` with the password only in `BACKUP_PASSWORD`, shows an "Action Needed" banner telling the user to look at the device and enter its passcode before the command starts (2-minute limit; the backup's own passcode request on iOS 16.1+ gets the same banner), and confirms `WillEncrypt` before the backup. The setting stays on. Every pull appends a record (`epoch-pulls.jsonl`, beside the backups) of the device, tool version, outcome, bytes received and whether the app changed the setting. A running backup shows the data received (the folder's growth) as a share of the size estimate, held at 99% until the tool reports the backup finished (the device's own percentage is not shown: on a real run it read 35–50% at 86 of about 96 GB), the time since data last arrived, the elapsed time and a Cancel button (SIGINT, as Ctrl+C would); after 3 minutes without data it asks the user to check the device. A folder left by a pull that didn't finish (Status.plist `SnapshotState` not `finished`) is offered for deletion and never deleted automatically; a deletion is recorded. *Changed 2026-10-12 (EPOCH-483): such a folder can't be resumed, and a pull refuses to write into it; "Keep It" was removed.* The app remembers the folders pulls wrote to, so it finds such a folder after the user picks another. Before anything on the device changes, the pull compares the destination's free space with an upper bound on the backup's size (data capacity less `AmountDataAvailable`; `TotalDataAvailable` counts purgeable space) and stops when it is short, as the device itself would (ErrorCode 105) | Linux has no Finder or iTunes, so refusing left no way forward. EPOCH-101's failure came from hiding the passcode request, not from the command. Changing a device setting is recorded because the device is evidence. Turning it back off would need the passcode again | EPOCH-466 |
| New Investigation asks first whether to pull from a connected iPhone or use an existing backup, then shows the pull's steps in order (device, destination, password, Pull); the backup password appears only once a device and a destination are chosen and is cleared when either changes or the pull starts. The main process keeps the running pull's state (device, destination, progress, stats, banner), so the view shows it again after a remount; while a pull runs, device queries are refused and its own folder is not offered as incomplete. Only a folder with a Status.plist, in a destination a pull recorded, can be deleted as incomplete. A completed pull's record is written before it reports done, and the record states the error | A real pull showed both import paths at once, asked for the password before there was a destination, and after the view remounted offered Pull again mid-backup (a second click queried the device); the failed run's record could not say why it failed | EPOCH-467 |
| A pull writes only into a new folder: a destination already holding anything for the device (a finished backup, an unfinished one, or an unreadable folder) is refused before the device is touched, and the panel says why before Pull is offered. A pull is reported complete only when the backup's `Status.plist` says `finished` and its `Manifest.db` exists. What the app says about device behaviour must match the verified list in [architecture.md](architecture.md#verified-device-behaviour) | A second pull to the same destination ran `--full` over a finished backup, which is evidence, and could run into an unfinished one. A real-device test showed an unfinished backup can't be resumed. Success had been reported on the tool's exit code alone | EPOCH-483 |
| The processor gives mvt-ios the backup password only in `MVT_IOS_BACKUP_PASSWORD`, with stdin closed *Changed 2026-10-13 (EPOCH-489): the decrypt receives it the same way, in `BACKUP_PASSWORD`.* | On the command line (`-p`) the password is visible in the process list for the whole decrypt (R30) | EPOCH-486 |

## App

| Decision | Why | Where |
|---|---|---|
| Run rows expand independently as inline accordions; side-by-side compare is deferred | Compare needs its own query shape and design | EPOCH-410 |
| The store keeps `selectedRunId` separate from `expandedRunIds` | Open rows and the run a view acts on are different things | EPOCH-410 |
| Finished runs' stages are fetched once; running runs' stages are refetched | A finished run is immutable | EPOCH-410 |
| A source type is complete if the latest run that attempted its stage is complete | A rerun that fixes only the failed files then shows complete | EPOCH-411 |
